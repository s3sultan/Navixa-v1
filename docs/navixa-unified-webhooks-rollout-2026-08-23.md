# توحيد Webhooks لبوابات دفع NAVIXA

**الحالة:** تصميم وفرع تكامل فقط. يظل التحصيل الحي وظهور Checkout العام مقفلين.

## المبدأ

تصل كل بوابة إلى نقطة Webhook مستقلة، لكنها تتحول داخل NAVIXA إلى حدث موحد قبل لمس الاشتراك أو الإحالات أو أسعار المؤسسين. لا يفعّل أي حدث اشتراكًا اعتمادًا على عودة المتصفح وحدها.

| المزود | المسار المستهدف | التحقق | التفعيل |
|---|---|---|---|
| Moyasar | `/api/billing/webhook` ثم مسار مخصص لاحقًا | `secret_token` مطابق للسر المحفوظ | الموصل استخرج في الفرع؛ لا تغيير في الإنتاج |
| Tamara | `/api/billing/webhook/tamara` عند العقد | توقيع Tamara الرسمي، ثم استعلام خادمي عن حالة الطلب | مخفي ومغلق حتى مفاتيح Sandbox وQA |
| Tabby | `/api/billing/webhook/tabby` عند العقد | Webhook إعلامي ثم استرجاع حالة `payment_id` من API | غير مبرمج حتى العرض والعقد |

## عقد الحدث الداخلي

يتحول كل Webhook إلى `NormalizedWebhookEvent` يضم المزود ومعرّف الحدث ومعرّف الدفع ومعرّف نية NAVIXA والحالة والمبلغ والعملة. قبل التفعيل يُفحص التوقيع، وفريدية الحدث في `navixa_billing_events`، وتطابق نية الشراء والمبلغ والعملة، ثم تُنفذ التسوية مرة واحدة فقط.

## الإطلاق الآمن

1. يضاف سر Sandbox فقط في Cloudflare.
2. يفعّل المدير مزود الاختبار من لوحة الإدارة، ويبقى Checkout العام مقفلًا.
3. تجرى حالات نجاح وفشل وإلغاء واسترداد وحدث مكرر في Sandbox.
4. تراجع سجلات الأحداث دون إنشاء اشتراكات حية.
5. تضاف مفاتيح الحي، ثم اختبار حي واحد مصرح به لكل وسيلة.
6. بعد توثيق النجاح فقط، يفتح المدير الوسيلة المحددة للزوار.

## أسرار Tamara المتوقعة

لا تضاف قبل العقد. عند الاستلام تحفظ مباشرة في Cloudflare كأسرار: `TAMARA_API_URL` و`TAMARA_TEST_API_TOKEN` و`TAMARA_LIVE_API_TOKEN` و`TAMARA_WEBHOOK_SECRET`. لا تحفظ في GitHub أو D1 أو واجهة العميل.
