# API حملة مؤسسي NAVIXA

## الملفات

| الملف | الغرض |
|---|---|
| `app/foundersCampaign.ts` | منطق الجداول، الحجز العشوائي، انتهاء الحجز، تثبيت الدفع، والعداد الحي |
| `app/api/founders/route.ts` | واجهة API لحالة الحملة وحجز السعر للحساب الموثق |
| `app/api/founders/honor/route.ts` | كشف امتياز المؤسس الذهبي بعد مرور أسبوع فقط |

## المسارات

### 1. حالة الحملة العامة

```http
GET /api/founders
```

**مثال استجابة:**

```json
{
  "available": true,
  "startAt": "2026-08-21T21:00:00.000Z",
  "endAt": "2026-09-22T20:59:59.999Z",
  "totalSeats": 100,
  "paidSeats": 37,
  "reservedSeats": 4,
  "remainingSeats": 59,
  "message": "توجد فرص مؤسسين محدودة متاحة الآن"
}
```

لا تكشف هذه الاستجابة الأسعار المتبقية في كل فئة أو هوية أي مستخدم.

### 2. حجز سعر مؤسس للحساب

```http
POST /api/founders
Content-Type: application/json
Cookie: __Host-navixa_session=...
Origin: https://navixasa.com
```

لا يحتاج الطلب إلى جسم حاليًا. يشترط جلسة NAVIXA مرتبطة ببريد موثق، كما يرفض الطلبات خارج النطاق الموثوق.

**مثال استجابة ناجحة:**

```json
{
  "ok": true,
  "foundersIntentId": "uuid",
  "priceHalalas": 900,
  "priceSar": "9.00",
  "expiresAt": "2026-09-20T10:15:00.000Z",
  "renewalPriceSar": "19.00",
  "note": "هذا سعر مؤسس لأول شهر فقط..."
}
```

**مثال رفض:**

```json
{
  "error": "لا يمكن تخصيص أكثر من عرض مؤسسين للحساب نفسه"
}
```

### 3. كشف امتياز المؤسس الذهبي

```http
GET /api/founders/honor
```

لا يعيد هذا المسار أي تلميح عن كون المستخدم أول مؤسس قبل مرور سبعة أيام كاملة من دفعه الموثق. بعد الموعد، يعيد اسم الشارة الذهبية وتاريخ انتهائها بعد عام. يبقى السجل محفوظًا داخليًا منذ الدفع، لكن الواجهة لا تعرضه قبل `unlock_at`.

## ربط Checkout

بعد الحجز، تمرر واجهة Plus القيمة `foundersIntentId` إلى مسار Checkout. يجب أن ينشئ Checkout نية شراء بالمبلغ العائد من `priceHalalas`، وأن يحتفظ بالمعرف نفسه داخل metadata لدى Moyasar:

```json
{
  "navixa_intent": "billing-intent-uuid",
  "navixa_founders_intent": "foundersIntentId"
}
```

يجب ربط `foundersIntentId` بنية الدفع (`intent_id`) داخل قاعدة البيانات قبل تحويل العميل إلى Moyasar.

## ربط Webhook

لا ينبغي استدعاء `completeFoundersAward` من المتصفح. بعد التحقق من توقيع Webhook وحالة `payment_paid` ومطابقة المبلغ والمرجع، يستدعي الخادم:

```ts
await completeFoundersAward(database, foundersIntentId);
```

تنفذ الدالة ضمن منطق الدفع الموثق فقط:

1. تغيّر العرض من `reserved` إلى `paid`.
2. تنقص `reserved_count` للفئة السعرية.
3. تزيد `redeemed_count` للفئة السعرية.
4. تثبت المقعد ضمن إجمالي الـ100.

## قواعد السلامة

| القاعدة | التطبيق |
|---|---|
| سعر واحد للحساب | قيد `UNIQUE (campaign_key, contact)` |
| منع التنافس على آخر مقعد | `UPDATE` ذري يتحقق من السعة قبل زيادة الحجز |
| حجز محدود | 15 دقيقة فقط |
| لا استهلاك من مجرد الزيارة | لا زيادة في `redeemed_count` قبل Webhook موثق |
| لا إعادة سحب | العرض المنتهي يسجل للحساب ولا ينشأ سعر جديد له |
| عدم كشف الفئات المتبقية | API العام يعرض الإجمالي فقط |
| عدم تخزين البطاقة | البطاقة تتعامل معها Moyasar فقط |

## اختبار يدوي قبل الإطلاق

1. أنشئ حسابين اختباريين ببريدين مختلفين.
2. افتح الحجز من كل حساب وتأكد من اختلاف `foundersIntentId` وسعر الحجز.
3. لا تدفع من الحساب الأول، وانتظر 15 دقيقة؛ يجب أن يعود المقعد للمخزون دون منح الحساب سحبًا جديدًا.
4. أكمل دفعًا اختباريًا من الحساب الثاني؛ يجب أن يزيد `redeemed_count` مرة واحدة فقط.
5. أرسل Webhook نفسه مرتين؛ يجب أن تبقى قيمة العداد دون زيادة ثانية.
6. جرّب حجزًا ثانيًا من الحساب المدفوع؛ يجب أن يرفض.
7. جرّب حسابًا ثالثًا مع آخر مقعد في فئة محددة؛ يجب ألا تتجاوز المقاعد الإجمالي المحدد.

## ملاحظة إطلاق

المسار منشأ برمجيًا، لكنه لا يفتح الدفع العام وحده. يلزم ربطه النهائي بـCheckout وWebhook، ثم تفعيل أسرار Moyasar وإعدادات D1 من حساب المدير قبل قبول أي دفعة حية.
